# SHA1 与 PickCode 取链只读对照

2026-10-06，应用户要求，在管理员共享小号的同一个真实文件上交替执行四轮只读查询。凭据固定，实例数据库只读，未写入网盘和生产缓存，未下载影片。每轮都请求 115，不复用上一轮 CDN 地址。

| 轮次 | SHA1 查询再取链 | 已有目标 PickCode 取链 |
| --- | --- | --- |
| 1 | 772 ms，2 次请求 | 254 ms，1 次请求 |
| 2 | 361 ms，2 次请求 | 263 ms，1 次请求 |
| 3 | 333 ms，2 次请求 | 249 ms，1 次请求 |
| 4 | 318 ms，2 次请求 | 221 ms，1 次请求 |

四轮 SHA1 查询均返回本地记录中的同一个文件。SHA1 路径为 `/files/shasearch` 一次 + `/app/chrome/downurl` 一次；PickCode 路径只有 `/app/chrome/downurl` 一次。目标响应字段足够，未发生精确元数据补查；目录检查、主账号请求和写入均为 0。后续三轮 SHA1 路径平均约 337 ms，PickCode 平均约 244 ms；这些数字只是单文件短时样本，不代表稳定性能保证。

当前已验证接口中，SHA1 用来定位目标文件，其响应提供 file ID、PickCode、大小等信息，并不提供 CDN 直链；仍需后续 PickCode 取链。如果直链响应缺少 SHA1，可能多一次精确核验。SHA1 快速接口也可能返回回收站旧记录，详见网盘操作实测，不能保证每次都两次请求完成播放。

建议让 SHA1 + 大小作为内容查找键，并按目标 UID 隔离副本；已有可信目标副本时优先使用其 PickCode，一次取链；无记录时按 SHA1 查找，再用结果 PickCode 取链，保存成功核验后的副本。源 STRM 的 PickCode 不等于目标账号的 PickCode：play115 完整声明不需要前置查询源 PickCode，但缺校验片段时仍可能用它取源文件；redirect115 缺大小时还可能需要源元数据。
