## 已复现的缺陷

运行：`go test ./internal/service -run '^TestDeviceAnalysis' -v -count=1 -timeout=120s`

| 场景 | 当前结果 |
| --- | --- |
| 同设备、同用户、同播放器，每 5 秒换一个会话，UID 容量 3 | 三次签发占满 3/3，第四次被拒绝 |
| 上述累积后再静默 100 秒 | 多个历史候选使接替永久跳过，直到旧记录到期或人工处理 |
| 每次正常停止后切下一片 | 用户记录已清零，但三条两分钟残余仍占满 3/3，第四次被拒绝 |
| 当前片静默 40 秒，下一片只申请直链，不上报 Playing | 被当成正式接替，旧片的新取链被封住 |
| 当前片仍有播放心跳，UID 容量 1，申请下一片预读取 | 预读取被当成第二个池名额而失败 |

实现位置：`user_playback.go` 的唯一候选及静默判断，`pool_media.go` 的会话/条目/媒体源池键，`playback_handoff.go` 的签发时切换，`playback_event.go` 的逐租约停止残余。

HTTP 代码检查另确认 GET 与 HEAD 都进入同一取链并 Commit 的路径；未区分“播放器已开始展示”与“播放器仅预读取”。Cinema115 没有主动预热任务，第三方播放器发来的预缓存请求仍按正常取链处理。未捕获本次用户的真实 Yamby 报文，因此不能断言其特定版本的预缓存事件顺序。

## 根本缺陷

1. UID 容量绑定短命播放会话，而非稳定设备通道。设备身份目前只是临时寻找旧租约的辅助字段。
2. 停止会删除用户记录，却留下计费中的池残余；用户和池生命周期脱节，下一片失去接替对象。
3. 唯一候选规则存在自我阻塞：一次未接替造成两条记录，以后都不能接替。
4. 签发 CDN 地址被误当成确认播放，预读取会提前退休当前影片；有心跳时又把预读取当成额外播放收费。
5. 会话代次与 UID 名额转交耦合，缺少独立的当前播放、候选预读、退休请求三种状态。
6. 设备锁横跨整个取链准备过程，下一片慢秒传可能让同设备当前片的新取链排队。
7. 没有报告停止时仍依赖长 TTL；接替并没有实现退出回收。

## 建议模型（待实施）

稳定键：Emby 服务 ID + 已验证用户 ID + 已认证设备关联 + 播放器标识。不要包含条目、媒体源、PlaySessionId 或原始 Token；Token 仅用于鉴权。一个设备通道固定占一个 UID 逻辑名额，内部管理多个有限生命周期的请求。

```text
设备通道 → 一个 UID 名额
            ├─ 当前播放 A
            ├─ 待播放/预读取 B（默认最多一个）
            └─ 已退休 A 的代次记录（不重复计费）
```

- 同设备换片、重开、换 PlaySessionId、更新 Token：复用设备名额，无须等待 30/90 秒，也无须从全部历史会话中猜唯一对象。
- 相同 UID 内下一片可以继续取链或秒传，但不额外消耗池名额；准备次数、写入并发与 API 频率分别受限，不能因复用名额放开请求限速。
- GET/HEAD/Range 只能创建或复用候选，不能单凭它们封锁当前影片。普通 PlaybackInfo 仍只做协商。
- 使用已认证 Playing/Progress 与会话/条目关联推进当前播放；处理事件先于取链、响应乱序、重复事件及失败重试。事件表达客户端声明的播放状态，不证明真实画面或 CDN 流量。
- B 被确认开始后提升为当前播放；A 进入有限过渡期，旧 A 的停止/进度不能取消 B，也不能重新把 A 设为当前播放。预读取 B 失败时 A 不变。
- 不上报状态的客户端无法可靠区分主动换片与预读。默认保留有界的当前和候选请求，沿用同一名额；不能声称仅靠第二次 GET 可以兼容所有播放器又严格识别真实播放。
- 默认一个当前播放、一个预读候选；若支持多候选客户端，应通过实测增加有界候选数量。限制的是设备内部任务，不恢复用户级单路限制，其他设备独立占位。
- 当前播放停止时只结束对应子会话。无候选则设备名额释放或进入短暂宽限；有候选则只保留一个设备名额，候选有固定到期上限。
- 残余信息按设备和 UID 合并，不能每切一片就再扣一个名额。同 UID 内退休记录只用于代次隔离；跨 UID 切换时旧 UID 保留独立、有界的残余，避免伪称旧连接已经消失。
- 强退无停止事件：使用设备级活动期限回收，期限需基于真实客户端上报频率验证。缓存到期、API 限流和设备活动期限分开；不能再把 CDN 缓存或长文件租约当成播放存活证明。
- 设备名额代次与播放子会话代次分开。UID/凭据变化、管理员强制释放校验设备代次；普通停止校验子会话代次，不清除整个设备通道。
- 设备锁只保护选择、状态变更和事务提交，不横跨网络 I/O；具体影片的准备按子任务去重，当前播放不被下一片长任务堵住。

## 实施前要明确的边界

302 已签发 URL 无法立即撤销。因此“一设备一个名额”是逻辑并发策略，无法保证真实 CDN 只有一个连接；当前播放加预读取本来就可能有两路读取。严格限制真实连接需要流量经过可控代理或上游支持可撤销授权，这与现有纯直链路径不同。

完全退出但没发停止，服务端不能立即知道。可以保证同设备重开复用同一个名额，并通过设备级超时解决无人重开时的回收；这两个问题需要分别实现。

## 下一版验收清单

- [ ] 同设备连续切换 100 次，同一 UID 的逻辑占用始终为 1，不依赖停止通知或静默等待。
- [ ] 正常停止/强退/换 Token/缺少 PlaySessionId 的设备关联规则明确，不能无声回退为逐影片扣名额。
- [ ] 当前 A 播放时 B 发 HEAD、GET、Range：A 保持可取链，B 不新增 UID 名额。
- [ ] B 报告开始后，迟到的 A 停止和进度不影响 B；事件先于取链也能正确关联。
- [ ] B 的秒传失败、请求取消、重复预读不会损害 A，候选数量和寿命有上限。
- [ ] 两台设备占两个名额，同一用户没有总单路限制；同设备第二个真实播放按明确策略处理。
- [ ] 正常退出释放对应设备名额；有候选时最多保留一份且有固定到期；失联按设备级期限回收。
- [ ] UID 失效切换、配置换号、残余合并不跨账号转移文件归属，池失败不回退主账号。
- [ ] 状态、名额、代次事务一致；崩溃重启后不重复计费，管理员旧页面不能释放新代次。
