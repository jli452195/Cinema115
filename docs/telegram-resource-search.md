# Telegram 用户账号与资源搜索

右上角管理菜单 → Telegram 配置 →「用户账号 / 资源搜索」（`/telegram/user`）。

1. 填写自己的 Telegram API ID / API Hash 和资源 Bot 用户名，点击「保存 API 配置」。API 凭据从 https://my.telegram.org/apps 申请；Bot 用户名支持带或不带 `@`。
2. 输入带国家区号的手机号，例如 `+8613800000000`，请求验证码并在页面填写。若账号启用了二步验证，继续填写密码。
3. 账号必须已经获得所配置资源 Bot 的使用权限。本项目不会代替 Bot 的认证、订阅或配额规则。Bot 改名后直接修改用户名即可，网页和订阅搜索会统一切换并清空旧搜索缓存。
4. 打开电影或剧集详情，点击「Bot 搜索」。后端读取 TMDB 中文标题，向配置的 Bot 发送查询；网页使用 SSE 流式响应，首批可识别结果会立即显示，后端再用短静默窗口收齐连续回复。每次搜索可能消耗配额。
5. 浮窗展示版本名称、大小、TMDB 匹配标识和剩余次数。点击「加载更多资源」后，新结果追加在已有资源之后，只保留最新的下一页操作；到达末尾后显示「已加载全部资源」。累计结果整体保存在搜索缓存中，重新打开浮窗直接返回已经加载的全部资源；刷新搜索也继续追加，不清空旧结果。在资源卡片点击「分享 STRM」，自动获取该资源的 115 链接，使用「115分享STRM」中已保存的播放地址、输出目录、后缀和过滤设置。后端按每条任务启动时的转存开关与所选账号处理：开启时比较分享者 user ID 和 Cookie UID，本人分享直接生成，其他账号的分享先转存、再用新分享生成；关闭时直接生成。卡片显示进度、成功数量或失败原因；一个资源返回多个链接时依次生成，单条失败继续处理其余链接。
6. 搜索和资源获取结果在后端内存缓存 24 小时，明确的「未找到资源」也缓存；重复打开弹窗无需再次查询 Bot。缓存最多保留 64 项，退出账号、修改 Bot 或重启后清空。点击「刷新搜索」主动绕过搜索缓存，可能消耗 Bot 配额。缓存中的剩余次数是上次查询时的值。

此功能使用 Telegram 用户账号，通过 MTProto 访问；与 `/telegram/bot` 中用于接收生成任务的 Bot Token 配置相互独立。当前使用直连网络。

## TG 频道配置（第一步）

在「资源配置 → TG 频道配置」（`/telegram/channels`）选择账号已加入的频道。频道功能共用 `/telegram/user` 的 API 凭据与登录会话，资源 Bot 可以留空；Bot 搜索入口仍要求配置资源 Bot。

- 打开配置页只读取本地已保存状态。点击「选择频道」后按需读取频道列表，可多选、本地筛选已加载项，并继续加载主列表及归档频道；不查询聊天历史、不发送消息。
- 点击「保存频道」后生效，取消不保存；取消全部勾选并保存可清空来源。列表或保存失败保留当前选择，列表过期时重新加载。
- 频道与实际 Telegram 用户身份关联。退出账号会清除频道选择，更换账号后不能沿用原账号的选择。频道信息与访问凭据复用 `telegram-user-config.enc` 加密保存，API 不返回访问凭据。
- 本步骤完成配置入口和频道管理，详情页聚合搜索将在下一步接入。

「实时日志」模块可选择「全部 / STRM / Telegram / 订阅」。Telegram 记录用户配置和登录操作、搜索结果摘要，以及 Bot 接收器启动、连接变化、分享消息入队、批次开始和回复失败；订阅记录首次入库检查、跳过搜索原因、自动搜索、匹配入队与生成结果；资源缓存命中、操作开始和回复更新记录在 DEBUG。不会记录手机号、API Hash、验证码、二步验证密码、Token、会话或 Bot 原始消息。空轮询不写日志，连接失败与回复失败在状态变化时记录。所有模块共用最近 2,000 条内存日志，重启清空；STRM 生成详情仍归 STRM，任务结果继续独立保存在 SQLite。

## 会话与请求

- API 凭据保存为 `data/telegram-user-config.enc`，用户会话保存为 `data/telegram-user-session.enc`，使用项目的加密存储。备份时保留 `JWT_SECRET` 和整个 `data` 数据卷。
- API Hash 不回显；验证码和二步验证密码不落盘。手机号及验证码散列仅保留在十分钟登录流程内，重启后未完成的登录需重新发码。
- 服务重启后，在配置页检查连接或从详情发起搜索即可恢复会话。页面显示的登录状态以最近一次操作为准；实际请求仍检查授权。
- 网页搜索、翻页、取链和自动追更共用串行队列，最多容纳 8 项未完成操作，每项最多 32 个等待页面；相同查询合并等待，不重复发送。排队最多 60 秒，开始执行后单次最多 45 秒，追更也遵守此上限。缓存读取不占网络名额；配置及登录操作仍与网络查询互斥。完成后关闭连接，不常驻轮询整个账号，也不扫描其他聊天。
- 搜索前记录目标聊天快照和发出消息的编号，优先按回复关系归属，明确回复其他请求的消息不会混入；历史消息编辑只接受当前翻页选中的消息。约两秒没有新结果后返回，多个回复合并。部分 Bot 不提供回复关系，此时仍依赖串行和迟到回复隔离；不要同时在官方客户端向同一 Bot 发起其他查询。
- 关闭浮窗只停止页面等待。尚未开始且没有其他等待页面的查询退出排队；已开始的查询由后台在时限内收尾、保存缓存，重新打开可接回正在执行的查询或读取缓存。服务停止会取消并回收查询，不自动重放未完成请求。
- 连接失败、排队超时、明确的发送拒绝不统一误报为“上一项请求超时”。已发送或发送结果不确定的操作未完整结束时，保留 60 秒迟到回复隔离，页面显示真实剩余时间并暂时禁用重试；不会自动重复发送查询。已收到的资源保留为带提示的部分结果，不能显示为已加载全部；缓存中的部分结果可稍后刷新补充。
- 流式响应包含排队、等待回复、收集回复状态；错误返回稳定分类及可重试时间。日志记录操作分类、资源数量、耗时、完成或失败原因；页面断开与后台结果分别记录，不包含凭据或 Bot 原始消息。
- 资源动作仅接受服务端生成的 24 小时有效标识；只跟进当前所配置 Bot 自身的资源深链接或下一页回调，不暴露上一页。不会点击悬赏、支付、订阅或权限申请按钮。
- 支持消息文本、Telegram 隐藏链接实体、直接返回的一个或多个 115 链接。单独一条链接可补齐消息中的提取码；多条裸链接不会猜测独立密码的对应关系。无法识别的内容保留在原始回复中。
- 只有点击资源卡片的「分享 STRM」才提交任务，打开弹窗和命中搜索缓存不会触发生成。全部链接一次提交给后台队列，按保存的转存开关和所选账号逐条执行；审核重试、任务日志和成功通知沿用统一流程。提交成功后关闭弹窗、刷新或离开页面都不会取消转存，重新打开弹窗会按保存的任务编号恢复进度，不自动重复提交。只有「停止任务」会调用后端取消接口，停止当前及尚未开始的链接，已发生的转存需要按日志核对。浏览器只保存任务编号及资源标识，不保存 Cookie、令牌或原分享链接。生成结果不使用搜索缓存代替真实写入，同一弹窗内成功的资源按钮会禁用以避免重复点击。
- 后端每批最多接收 100 条链接，网页手动 Bot、Telegram 和订阅自动资源共用最多 20 批的 FIFO 队列；批次开始执行后最多五分钟，等待排队不占用执行超时。接收前保存所有子任务并固定整批账号凭据和设置。近期进度保存在内存中，保留最多 100 批，提交新任务时清理超过一天的已完成进度；长期结果在分享日志中查看。关闭浏览器不会中断任务，但后端停机仍会取消执行并保留检查点，不自动重放不确定的转存或删除操作。

## 构建

引入纯 Go 的 `github.com/gotd/td v0.110.0`，无需 CGO。开发使用 64 位 Go，编译并发和垃圾回收使用 Go 默认值，无需额外设置 `GOGC`、`GOMAXPROCS` 或 `-p`。Docker 通过 BuildKit 缓存模块和编译结果，支持 Linux amd64/arm64，运行时由单个 Go 服务提供前端与 API。

在 `backend` 目录下编译（PowerShell）：

```powershell
$env:CGO_ENABLED='0'
go build ./cmd/server
```

验证脚本和模拟响应放在 `tests/browser/`，不进入 Git 与 Docker。真实联调只在用户完成登录后执行，避免无授权发送 Bot 消息。
