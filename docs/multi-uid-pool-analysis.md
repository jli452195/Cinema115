# 多 UID 秒传与播放名额隔离验证

日期：2026-10-03。

第二阶段更新：同设备换片现已复用稳定名额，跨 UID 历史限制为最多三个未到期 UID；下表保留旧架构分析结果，最新验证见 [设备名额验证](device-slot-validation.md)。

后续调整：池租期默认已从 240 分钟改为 5 分钟，下表中的 240 分钟是调整前的测试结果。已保存的池设置优先于默认值；修改默认值不会重写已有租约的到期时间。第一阶段修复已将新故障切换残余限制为最多 2 分钟，并修复仅取链就退休旧会话的问题；相关测试已更新为修复后预期，见 [第一阶段验证](playback-phase-one-validation.md)。其余快速换片累积和固定设备槽位仍待第二阶段。

本次为本地隔离场景验证，使用临时存储、测试数据库和模拟 115 客户端。未修改运行中的配置、账号或租约，未调用真实秒传接口，未进行线上流量灰度。真实环境只有一个小号，因此多 UID 行为通过模拟账号验证。业务代码没有修改；设备固定槽位仍是待实现方案。

## 结论与计数口径

不能按“一个 Emby 用户固定占一个 UID”理解现有实现。当前按池租约计费，多个会话可以消耗同一个 UID 的多个名额，也可以分布到多个 UID。配置入口相同或不同都不能代替实际 UID 的容量归属。

秒传资料来源、目标写入和播放占用是三类状态：

- 只读来源提供已验证副本的文件信息或片段哈希，不创建播放池租约。来源自己的读取忙碌、冷却和接口限速仍然有效，不代表零资源消耗。
- 自动播放准备在选定目标上占一个准备名额，秒传成功并签发链接后转为已签发名额，不再另加一个“秒传名额”。目标不能随校验来源轮换而改变。
- 管理员手动秒传任务也临时预留目标池容量，但不创建正式用户播放记录；正常结束后释放准备名额。
- 已签发链接的旧目标在故障切换后可能留下残余名额。逻辑名额不是 115 CDN 的真实连接数，也不能立即撤回已签发链接。

## 测试矩阵及实际结果

| 场景 | 结果 |
| --- | --- |
| 为目标 D 秒传，来源 A、B 读取失败，C 提供校验片段 | 三个来源共 0 个播放名额；D 准备时 1 个，提交后仍为 1 个；副本归属保持 D |
| 从未签发过链接，前两个目标探测失败，第三个成功 | 失败目标预留被释放；全过程最多 1 个准备名额，最终总计 1 个，无残余 |
| 同一个已签发会话依次发生两次 UID 故障切换 | 总计 3 个：1 个当前、2 个旧目标残余 |
| 上一场景静默 3 分钟，没有任何停止事件或后续续租 | 仍然 3 个；普通故障切换保留原租期，默认 240 分钟，并未缩短为 2 分钟 |
| 上一场景继续推进模拟时钟，超过租期且无续租 | 计数归零 |
| 同一用户三个独立会话，每个 UID 容量设为 1 | 三个 UID 各占 1 个；没有用户级单路限制 |
| 同一可信设备、用户、播放器每隔 5 秒换片，不上报停止 | 三个 UID 各占 1 个，三个记录仍被分类为活跃；现有条件接替未触发 |
| 管理员手动秒传 | 写入期间目标 1 个准备名额，正式活跃播放 0；结束后目标占用 0 |
| 来源读取错误或目标写入结果不确定 | 不能触发目标故障切换；测试中的未签发预留关闭后释放 |

这些通过的测试包括“复现现有缺陷”的断言，不表示相关缺陷已经修复。故障切换案例中的 3 个不是生命周期上限：最多 3 次尝试限制的是单次请求，后续请求可以继续切换并留下更多残余。

## 已定位的设计缺陷

1. 会话/条目是计数单位，设备只是满足静默条件时才参与接替。快速退出换片跳过接替，多小号只是让堆积扩散到更多 UID。
2. 普通已签发会话的故障切换，将旧记录保存为 `residual:*` 时保持原 `ExpiresAt`；默认是 240 分钟。正常停止与设备跨 UID 接替另有 2 分钟残余处理，路径不一致。
3. “准备、活跃、残余”来自本地租约状态；未收到客户端停止事件不能证明客户端仍在播放。“活跃”统计可能含已退出设备的历史签发记录。
4. 单请求尝试预算不限制设备整个生命周期的跨 UID 残余链。只增加池账号或只缩短普通停止残余时间都不能解决根因。

代码入口：`backend/internal/service/playback_donors.go` 的 `readPlaybackMaterialRange`，`dynamic_pool.go` 的 `reserve`、`releaseUnissued`、`Commit`，`pool_media.go` 的 `PoolTargetFailed`，以及 `instant_upload.go`。

## 建议的后续实现约束

- 容量按服务、Emby 用户、可信设备、播放器的稳定槽位管理；正式用户会话生命周期仍分别记录，允许其他设备独立播放。
- 同设备换片优先复用原 UID。播放 A 和有界预加载 B 共用该槽位；取到 B 的链接不直接判定 A 已结束。
- 来源小号只走只读校验调度，继续遵守按 UID 去重、最多 3 来源共用 4 秒预算；不申请播放容量，也不改变目标。
- 槽位内新的目标写入保持固定凭据和目录，写入结果不确定时禁止跨 UID 重试；按 UID 的写入串行与播放容量分别管理。
- 已签发后确需换 UID 时，显式记录当前槽位与旧 UID 残余，统一残余期限和不可续租规则，并限制连续切换形成的残余链。正常目标是“当前 1 个槽位”，跨 UID 切换期间可能多出残余；不能承诺任意时刻总是 1 个。
- 用正式播放证据、停止事件、设备空闲回收共同更新状态；旧会话的迟到事件不得释放新槽位，预加载不能挤掉当前播放。
- 后续验收应覆盖同设备连续 100 次切片仍只有一个当前槽位、A+B 预加载、跨 UID 故障链、旧事件乱序、并发请求和重启恢复。真实 Yamby 的预加载与退出事件时序仍需接入验证。
