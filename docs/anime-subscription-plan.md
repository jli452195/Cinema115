## 1. 目标与已确定的方向

管理员从 Bangumi 新番日历选择具体动画篇章，确认对应的蜜柑资源与字幕组后建立订阅；默认从指定集数补当前能找到的资源，并持续发现符合条件的新发布，下载到主账号的 115 网盘，按需自动命名并归档到指定目录。

本模块的业务范围只有订阅、下载、整理，以 115 实际文件核对和归档结果为完成依据。Emby、STRM、影视追更关联、播放和外部通知均不在本模块范围；模块使用现有管理员鉴权，不要求配置媒体服务器。复用限于元数据读取、115 网盘能力、存储与通用 UI，不依赖其他业务的索引、回调或生命周期。

当前已确定的方向：

- 第一版以 Bangumi 新番日历为主入口，同时提供历史番剧搜索；不要求先选 TMDB 作品。
- 选定篇章后再确认蜜柑资源条目与字幕组；Bangumi 提供资料和作品关系，蜜柑提供资源发现，TMDB 仅用于可选的作品资料、季集对应与整理命名。
- 首次订阅默认从指定集数开始补当前能找到的资源，启用前预览实际匹配结果；起始集数的编号语义和初值建议见第 6 节。
- 起始集数按字幕组标题编号填写，预览显示已确认的对应篇章集号。
- 115 采用“番剧目录 / 每条下载资源独立子目录 / 原文件”的布局，便于核对与恢复。
- 按具体放送篇章、发行版本管理资源，不把整个系列强行当作一个季。
- 一个订阅可配置主 RSS 和备用 RSS；采用多字幕组版本共存，不按集号互斥下载，不洗版、不自动替换或删除已有版本。
- 115 离线提交、状态追踪和恢复由 Cinema115 自己实现。
- 视频保持原文件，不新增本地视频下载、转码或重新封装流程。
- 启用整理时直接改名、移动原视频，原位置不保留重复视频；最终文件读回成功后结束任务，不再轮询该条离线状态。
- 前端方案与交互由 Gemini CLI 参与讨论、审查；后端设计、实现与审查由 Codex 负责。
- 按实施任务表逐项推进；P0 先验证上游能力，不创建真实 115 下载任务。

已获取的名称、封面引用与版本说明保存本地快照；刷新资料不会覆盖管理员确认的版本和映射。外部封面失效时保留已有缓存或占位，正常订阅不依赖封面下载成功。

P0-01 已只读验证公开 `/calendar` 返回七个星期分组，条目含 ID、名称、放送开始日期与星期等资料；历史搜索使用 `POST /v0/search/subjects` 的动画筛选与 limit/offset 分页。详情和条目关系支持本次 Last-Modified 条件读取，返回 304。具体参数、样本、错误与缓存行为见 [Bangumi 接口验证报告](anime-bangumi-api.md)。

周历不是“这一季度全部作品”的接口，不假定支持季度参数；首版做实际返回的周历与独立历史搜索。搜索为上游实验性接口，本地必须校验非空关键词；季度目录与完整历史覆盖仍不作承诺。2026-10-21 的 E-01 已核实蜜柑、AniBT、Anime Garden 各自真实季度接口及索引，以站点收录为范围接入季度浏览；不使用 Bangumi 周历冒充季度目录，详见[季度浏览实现与验证](anime-quarter-browsing-implementation.md)。

## 3. 业务对象与责任边界

区分以下对象，分别记录订阅配置、下载事实和整理结果：

1. **动漫条目**：本地的具体放送篇章或发行版本，例如某季前半、某季后半、新编集版。系列关系只是展示分组。
2. **资源订阅**：这个条目使用哪个资源源、字幕组、过滤条件、初次抓取范围以及下载目录。
3. **发布条目**：RSS 中的一条资源及其原始标题、资源 Hash、解析结果。
4. **下载任务**：本工具对一个资源的实际 115 提交和后续核对记录。
5. **实际文件**：下载后核对到的网盘文件，身份为实际 115 UID 与文件 ID。
6. **整理命名映射**：字幕组原始集数与目标命名季集的对应规则及其版本。

动漫订阅独立保存配置、发布记录、下载任务和整理阶段；其他业务的订阅、索引或完成状态不参与本模块调度与判断。

首版建议仅管理员管理资源订阅。普通用户的自助动漫订阅、独立配额和个人网盘下载留待独立讨论。

界面统一使用“新番日历”“动漫订阅”“字幕组”“下载记录”等业务词。内部“条目”“发布决定”“提交意图”不直接成为菜单或配置字段。点击日历卡片先查看选定篇章，再“选择资源”；确认蜜柑对应版本与字幕组后才进入规则预览，不把点进详情等同于订阅。

相同 Bangumi 篇章或已确认来源再次配置时优先定位已有本地条目；相同规范化 RSS 重复添加时提示已有配置。主 RSS 与多个备用 RSS 分别绑定来源/组及编号规则，允许同一集不同字幕组、不同 Hash 的资源同时保存，不建立分集独占约束。TV 原版与新编集版仍使用不同条目；名称相同或蜜柑页面存在一个 Bangumi 链接都只能提供关联候选，不能据此自动合并实际资源。

来源关联记录选定的 Bangumi 篇章、蜜柑条目、字幕组、适用篇章范围、编号规则、依据与确认版本。一个蜜柑条目可能包含多个篇章；需显式限定适用范围，不能因它关联了某个 Bangumi ID 就订阅该页面的所有发布。无法可靠限定时只保存待处理候选，不自动下载。

## 4. 《Re:0》这类作品怎样表示

### 4.1 分别保存版本与篇章

| 情况 | 处理方式 |
| --- | --- |
| TV 原版与新编集版 | 分别建立本地条目；分集长度或内容不同，不能只改偏移量合并 |
| 同一季前后半、不同篇章 | 从 Bangumi 选择具体篇章，再核对蜜柑发布覆盖范围；分别订阅后可确认归档到同一作品目录 |
| 字幕组从 1 开始或延续前篇编号 | 显示字幕组原始编号；必要时确认它与当前篇章序号的对应，之后才处理可选的命名映射 |
| 不同站点对同一篇章有不同划分 | 保留各来源身份，管理员确认归属；不按名称自动合并 |
| SP、OVA、总集篇、12.5 集 | 保存原始类型和编号，独立处理，不挤入正片集数 |

P0-02 已实测蜜柑 701（原版）、2153（新编集）、2259/2348（第二季前后半）、3464（第三季袭击篇）。3464 内同时有反击篇与 51–66 话合集，2259 有 26–50 话合集，外链不能代替逐条范围核对；新编集还出现 07A、06B 等编号。原始样本、RSS 与历史边界见[蜜柑资源与历史验证报告](anime-mikan-api.md)。

例如“源站第 25 话映射为目标 S02E01”只能是一条经过确认的规则，不能从“第二季”三个字自动推出，也不代表《Re:0》的通用编排。

### 4.2 分集标识

分集同时保留发布原始编号及其稳定编号空间（来源、字幕组和已确认的编号体系），解析与规则版本另存快照。篇章、类型与已确认篇章内编号用于归属、展示和命名，多条不同资源可以关联同一集；不是下载互斥键。未确认对应时保留原编号空间，不把两个字幕组相同的数字直接视为已确认同一集。保留发布原文，不使用浮点数作为特殊编号的唯一身份。修正对应须预览既有文件和命名影响，不清空处理历史或重新下载相同 Hash。

区分两层对应关系：

1. **选番与资源对应**：Bangumi 选定篇章，字幕组发布可能从 1 开始，也可能沿用连续编号。预览显示“字幕组编号 / 当前篇章序号（已确认时）”，未知则显示“未确认”。来源涵盖多个篇章时，必须先确认适用范围。这是可靠选资源所需的规则，不涉及 TMDB。
2. **整理命名对应**：把已经确定的分集再对应到选定 TMDB 资料的目标季集，用于目录与文件名；属于第 11 节的可选能力，下载不以完成此配置为前提。

例如某来源连续编号第 25 话，经管理员确认后对应当前篇章第 1 话，仍需另行确认目标命名是否采用 S02E01。版本重剪、两集合一等情况不能用同一个固定偏移掩盖。

资源中的 v2、修正版、REPACK 是发布版本，不是新增一集。符合各自规则的新 Hash 可以作为独立版本保存，旧版本保留；不覆盖、不自动挑选胜出版本，也不把同集多个文件计为多集。

### 4.3 资料变化

Bangumi 总集数、源站 END 标签、最大已发现集数都不能单独触发“全剧已完成”。首版建议由管理员归档；自动完结判断作为后续能力，单独讨论依据。

| `/anime` | Bangumi 新番日历为主视图，提供历史番剧搜索 |
| `/anime/subscriptions` | 已配置的资源订阅 |
| `/anime/subscriptions/:id` | 订阅详情、资源记录与下载进度 |
| `/anime/settings` | 本功能下载目录、抓取周期及可选后处理设置 |

这些是建议路由，不意味着新增一套独立导航或账号体系。主入口的新用户视图确定为新番日历；菜单归属以及已订阅用户是否恢复上次管理视图仍可讨论。

### 5.1 新番日历与历史搜索

- 首版以 Bangumi 周历展示当前接口提供的作品，建议默认选中今天，提供星期切换；桌面与手机均避免把七列完整海报墙同时挤在屏幕上。
- 顶部提供明确的“搜索番剧”入口以查找历史作品；从历史搜索选中同一篇章后进入相同流程，不要求它还出现在当前日历。
- 日历用 Bangumi 名称、封面和放送资料，不在每张卡片上请求蜜柑或资源可用性。说明“按原始放送星期展示”，不标成字幕组更新承诺，也不凭放送资料显示可下载。
- 点击后在同一详情/创建页面查看具体版本与前后篇关系，按需读取 Bangumi 详情，再加载蜜柑候选；不预抓整个日历的资源列表。
- 面板先复用卡片已有的封面、名称和放送资料即时显示；篇章详情与资源候选分别显示局部加载状态，失败可分别重试。更新不清空头部、不将整个页面切为 Loading，预留合理尺寸以减少跳动。
- 候选优先利用已知来源关联，并结合名称、别名、年份与篇章提示；结果始终展示 Bangumi 选择和蜜柑原名，管理员确认后使用，不凭标题相似自动绑定。
- 复用现有蜜柑客户端、资源展开、封面缓存、请求合并与访问间隔；资源历史只在选定来源和字幕组、预览首次范围时读取。
- 没有合适来源时可“保存待选资源”，在管理列表显示“待选资源”；这只是选番草稿，不显示已启用、不启动后台下载。后续可手动搜索蜜柑并继续配置。
- 日历读取失败保留上次成功内容和更新时间，可重试或使用已缓存资料；既有 RSS 订阅继续运行。没有缓存时显示真实空态，不伪造作品或自动改为其他主入口。
- 现有蜜柑搜索弹窗保留“订阅此字幕组”快捷入口，进入同一创建流程；已确认的篇章关联可复用，未关联时可补选 Bangumi，仍不强制 TMDB。

### 5.2 创建订阅

建议采用一个连续配置面板，分为三个区域，手机独立页面、桌面可用侧面板，不连续叠加多个弹窗：

1. **篇章与资源**：保留 Bangumi 所选作品及版本/篇章，确认主 RSS 对应的蜜柑条目、适用范围与字幕组，按需增加备用 RSS。每条来源分别确认，不把主源编号套给其他组；尚无有效主源时只保存待选资源草稿。
2. **规则与首次范围**：每条 RSS 的画质、包含/排除条件、原始编号与首次范围独立，默认“从指定集数补已有资源”。输入标为“从第几集开始补”，附说明“按该字幕组标题编号，包含本集”；常规初值 1，已确认连续编号对应时展示换算建议。
3. **预览与启用**：展示当前匹配的发布、集号与跳过原因，核对保存目录，再“保存并启用”；配置齐全时也可“保存为暂停”。

三个区域按依赖渐进展开：初入页面只展开篇章与资源，确认有效来源及字幕组后展开基础规则，预览完成才展示下载清单和启用动作；已完成区域可折叠为可编辑摘要，不铺满不可用表单。高级配置保持折叠，不默认替用户选未确认的画质。手机底部操作区只展示当前可执行动作，预留安全区和正文空间，不遮挡最后一条资源。

日历流程保留选定的 Bangumi 关联；启用下载还需已确认的资源来源、字幕组、范围规则和有效下载配置。蜜柑快捷入口可暂缺 Bangumi 关联；两种入口的下载都不要求 TMDB。主账号由系统统一管理，不提供账号选择器。没有主账号或目录时仍可保存选番草稿，不能把不完整草稿作为已启用订阅。

关键词规则默认折叠，首版使用字面包含/排除词，不提供任意正则或脚本。每条 RSS 的画质必须明确选择一个标题画质或“不限制”，不替用户预选；条件通过的不同 Hash 可以作为同集多版本保存，不按集号去重。修改某来源规则或首次范围使相应预览失效。保存携带配置版本、预览标识和操作幂等键，重复点击不建立重复订阅。

预览不提交 115 任务、不改网盘文件。按钮与保存结果按下表区分，不以醒目黄色或整卡警告表现普通的无资源情况：

| 当前情况 | 主操作 | 可保存结果与说明 |
| --- | --- | --- |
| 未选择来源，或篇章范围/目录尚未确认 | 继续配置；无来源时可“保存待选资源” | 仅草稿，按未完成项显示提示，不参与调度 |
| 来源与规则已确认、下载配置有效，但历史读取失败 | 重试读取 | 可“保存为暂停”，保留设置和读取错误，不创建下载任务，启用前重新预览 |
| 读取成功、规则有效，本次匹配 0 条 | 启用并等待资源 | 可保存暂停；说明“本次下载 0 条，后续按已保存规则检查”，不能把解析或归属不明归为零匹配 |
| 没有可执行资源，但存在解析或归属待确认项 | 查看待确认 | 可保存暂停；未确认项不包装成普通零匹配后直接启用；同集多个符合条件的 Hash 本身不算歧义 |
| 读取成功、存在已选历史资源 | 启用并下载已选 N 条 | 可保存暂停；显示实际集号、加载边界和目录 |

来源读取失败不能当作空结果；篇章归属或解析不确定的资源保留待确认。配置未完成的来源保存草稿，已有完整有效配置但暂不执行才保存暂停。未配置完成的备用源可单独保留草稿或移除，不阻塞有效主源；新建订阅仍须先有有效主源。上表的读取、匹配及待确认结果按来源判断，不因单源失败阻止其他已确认来源。

上表启用动作在 P2 下载能力验收后开放；P1 仅保存草稿/暂停配置，明确尚未启动下载。存在已选 N 条及另有 M 条待确认时，可以仅启用明确选择，摘要同时保留 M 条待确认。继续加载失败但仍有有效部分预览时保留该清单与加载边界，不把它改成空结果。

确认区用内联摘要展示“所选篇章、资源来源、字幕组、画质、起始编号和实际下载目录”，启用按钮按上表说明当前动作，次按钮为“保存为暂停”。默认范围示例：“从字幕组第 5 话起，本次匹配 4 条发布：第 5、6、8、9 话；第 7 话在已读取范围内未找到，启用后继续检查新发布。”多个发布核验为相同 Hash 时关联同一资源任务，保存后分别反馈新建和关联数量；实际文件数以下载后核对为准，不能把 4 条发布写成 4 个新任务或文件。

历史不完整时，确认区额外说明“更早历史尚未加载，本次只下载已预览选中的 N 条；剩余历史需继续加载后再补”，旁边提供“继续加载历史”。尚未读取的集数不能标成缺集，也不暗示后台会自动补齐未预览历史。确认后列出已建立任务的数量；预览之后新增的发布另按正常轮询处理，不悄悄混入初批数量。

仅新增发布不使原候选快照自动失效；规则、来源、账号目录版本变化或预览超过有效期才要求重新预览，保留全部输入并说明原因。前端可提示“订阅已启用，预览后新发布将按规则继续检查”，不保证未知或有歧义的新资源一定下载。

### 5.3 订阅列表

复用项目现有卡片外壳、悬停效果、浮层和官方 SVG 图标，动漫业务内容使用独立组件。

每项默认显示：封面、Bangumi 篇章名称（快捷入口未关联时用来源原名）、版本/篇章、主字幕组与“备用 N 个”摘要、订阅启用状态、最近检查时间，以及“待处理/下载中/需处理”的数量摘要。各来源名称、画质、原始编号与独立健康状态放在详情；不把主源失败表现成全部来源停止。待选资源草稿显示配置进度和“继续配置”，不展示无意义的下载统计或启用开关。

卡片只展示订阅、下载与整理摘要；详情的“整理命名（可选）”区说明原名保存或自动归档设置。抓取、网盘和整理异常在相关位置说明，不用一个总状态把整卡染成高饱和颜色。

主要操作为启用/暂停、检查更新和查看详情。暂停时显示“已暂停订阅”；若已有任务则附次级文字“已有 N 个网盘任务继续追踪，暂停后不再提交新任务”。检查后提供内联结果，例如“发现 3 条候选；订阅已暂停，本次未提交”。暂停原因和异常说明可展开查看，避免每张卡片堆积完整日志。菜单、卡片和开关均有文字标签或无障碍名称。

### 5.4 详情与恢复现场

- 概况与发布记录分开；列表按资源展示，明确一条资源可能包含多个文件或多集。
- 默认展示已选中的资源和需处理项，被过滤的记录可按需展开查看原因。
- 分别显示资源匹配结果、115 下载状态和整理状态；未启用整理时显示“原名保存”，启用后显示“待整理、整理中、整理完成或需处理”。状态由本地记录与 115 文件核对产生。
- 原文件名、完整目录、映射前后编号和错误细节放在详情中，支持复制。
- 桌面侧面板与手机详情路由共享状态，支持直接打开和刷新，关闭后返回原列表位置。
- 筛选、分页与选中详情进入 URL；缓存保存最后成功数据、滚动和展开状态。返回页面先恢复内容，再按有效期后台更新，失败保留旧数据并显示更新时间。
- 后台更新按稳定 ID 合并，保持卡片和操作区尺寸，不整页重建、不重播入场动画。
- 手机触控操作不依赖 hover；键盘、焦点返回、长标题和 reduced-motion 在实现阶段验证。

## 6. 初次抓取与筛选规则

### 6.1 首次范围与起始集数

| 选项 | 行为 |
| --- | --- |
| 从指定集数开始补已有资源（用户已确定默认） | 按已确认篇章范围内的字幕组原始集号，包含起始集；补当前能找到且符合条件的发布，再持续追踪新资源 |
| 仅订阅后的新发布 | 首次可靠读取建立历史基线，不立即把当前历史资源全量提交 |
| 选择当前历史资源 | 从明确加载到的资源中选择，展示本次实际提交数量 |

**起始编号语义已由用户确定**：按所选字幕组标题编号填写，预览显示对应篇章集号（对应关系已确认时）。首版使用“从第几集开始补”，说明“按字幕组标题编号，包含本集”；常规初值 1 为实现默认，数值范围 1～99999，不以 Bangumi 总集数或 TMDB 目标集数解释。无差异时用简洁的“字幕组/篇章：第 5 集”显示对应，确有差异时再显示“字幕组第 25 话 / 当前篇章第 1 集”；未知则明确为“篇章集号未确认”。若按篇章第 1 集表达起点，需先确认第 4.2 节的来源编号对应，再建议换算为来源起始号，不能自动用最新/最小已见集数推断偏移；来源历史里没找到第 1 话也不能证明它采用连续编号。

起始值是持续订阅的下限，不是仅首次生效的临时筛选。篇章覆盖范围先于起始值校验；跨篇章合并来源还需要已确认的上界或其他可核对的范围条件，不能把“第 25 话及以后”理解为后续所有季都下载。首版数值输入只覆盖正片整数集号，12.5、SP 与合集按独立类型保留候选，不强行转换为整数。

各 RSS 均保存自己有效预览对应的已见资源身份、快照实际读取时刻、预览生成时刻与启用时刻：追新 T0 取该快照实际成功读取时刻并按来源时间精度取整，缓存命中不后移 T0，避免缓存至启用之间发布的资源被漏掉；15分钟有效期另从预览首次生成时计算。“仅新发布”将首读资源设为历史基线；默认补历史或逐条选择则按各自已确认清单建立任务。抓取失败不建立假基线；有可靠发布日期时按边界筛选，日期缺失、异常或明显补录历史时进入待确认，不用“第一次看到”直接等同于“刚发布”。新增备用源不继承主源的已见集合或原始集号下限。

RSS 没有已验证的完整历史标志；P0-02 的样本含多年发布，某组与完整展开集合一致，但不能推广为全站完整性保证。补历史使用现有番剧资源累计展开能力或其他明确的历史读取接口，告知加载范围；不能把 RSS 当前列表称作整部全集。累计取满只表示可能还有内容，需继续探测；到达本地预算或保护上限仍不能确认末尾时保留未读完整。

创建面板不笼统承诺“补齐全集”，而是显示“下载当前已加载的历史资源”，附实际数量、已发现集号与是否还有未加载内容。例如“已加载 5 条发布，匹配第 16、18、20 话；更早内容尚未读取”，不能把有断档的集号缩成连续已齐范围。

历史预览记录来源分页边界、加载时间和候选快照；读取设预算，超过预算明确显示“还有历史未加载”并可继续加载。初批下载仅选用有效预览中已选中的资源，尚未加载的历史不在后台静默变成全量补番；补更多历史需继续预览。日常新发布继续按已保存的篇章、起始值和筛选规则处理，不绕过下限；新发现的旧历史或日期不明资源先保留候选，避免将来源补录误当成新一集。

首版历史预览每次最多 3 个未命中缓存的元数据请求、45 秒与 8 MiB 总正文，单响应 4 MiB；同一创建/编辑预览各来源已加载快照合计最多 2000 条原始发布且 `take<=2000`，不按 Hash 合并后计算。每条来源预览从各自首次成功生成起 15 分钟有效，继续加载不延长；整体预览汇总来源及各自有效期，不共用起点或续期。跨页和继续加载保留选择；明确取消的发布不在下一轮自动重新选中，也不新增永久集数排除规则。详细失败与末尾判断见[首版规则第 3、4 节](anime-first-release-rules.md)。

蜜柑无时区发布时间按固定来源时区 `Asia/Shanghai` 解释，属于实现默认，不是已验证的上游事实；原文与解释版本另存。T0 之后、未在基线中且时间可信的新发布才进入持续选择，早于 T0 的补录或日期异常保留待确认，不使用机器时区或首次发现时间替代发布时间。

创建预览与真正启用之间新增的资源不混入初批清单，后续按正常新发布流程处理。相同资源已在本工具确认下载则跳过；本工具无法确认的外部既有文件不按文件名假定已拥有，也不做全盘扫描。缺某集只表示当前指定来源和规则下未找到，不把 Bangumi 预计总集数写成必然可下载的全集清单。

### 6.2 匹配顺序

每条 RSS 分别执行：来源与字幕组核对 → 原始标题解析 → 版本及篇章范围核对 → 该来源起始集数与首次范围 → 包含/排除条件 → 画质条件 → 发布/Hash 幂等判断 → 保存执行决定。

- 首版一个订阅支持一个主 RSS、最多 4 个可选备用 RSS；各自绑定受控蜜柑条目/组及独立规则。采用版本共存，不等待主源失败才下载备用，也不在主源后到时覆盖备用文件。
- 画质采用可解释条件，例如“只要 1080p”；未知画质不自动满足明确的画质条件。
- 优先复用已核验磁力及来源对应；P0-02 的蜜柑 RSS 只有种子链接，没有磁力字段。只有种子链接且无可交叉确认身份时，通过受控来源取得种子元数据并计算实际 info-hash，不把 URL 文件名中的 Hash 直接当已验证资源身份。
- 首版沿用已支持的 BT v1 磁力范围；不支持的协议或无法核验的种子进入待处理。
- 集数提取优先覆盖常见 `- 01`、`[01]`、`EP01`、`第01话` 等格式，排除年份、分辨率等干扰数字。
- A/B 后缀、`[59][3rd - 09]` 复合编号、正片与 SP 混合范围保留原文，未确认前不截成普通整数集；编号体系按字幕组和版本分别核对。
- 自定义规则与解析版本均保存。规则变化可重新预览历史记录，不自动重新下载已完成内容。
- 合集、多集范围、无集号、含糊版本在首版保留为待处理候选，不按单集猜测下载和整理。

### 6.3 资源幂等与版本共存

按已验证资源 Hash 防止同一资源被轮询反复提交，保留来源发布与操作幂等记录；不按本地篇章/集号建立独占，不阻止同集不同字幕组或同组不同 Hash 的资源保存。编号对应只用于篇章归属与可选命名。主、备用 RSS 配置独立，停用一源不清理其他源或已存版本。

RSS GUID 不充当唯一发布身份：P0-02 实测相同 GUID 指向不同 Episode。保存来源原帖标识、原 GUID 和标题，按可核对的发布身份分开记录，再使用已验证资源 Hash 去重下载，不能因 GUID 相同覆盖另一条发布。

在同一事务中保存选中发布、资源幂等认领和下载意图，避免两个轮次对同一 Hash 重复执行；实际 UID、协议与 Hash 的写协调仍遵守第 8 节，不接管归属不明的外部任务。规则更改、增删 RSS 和取消再启用不清空处理记录。结果未确认的 Hash 继续对账，不影响同集其他 Hash。

首版各来源符合条件的资源分别选择，历史资源仍以本次预览勾选为准；同集两个不同 Hash 可以都被选中。排序只用于稳定展示，不实现“胜出版本”。不洗版、不替换、不自动删除旧版本；同一资源的显式失败重试先核对旧尝试，与收取另一版本分开。

## 7. 暂停、归档与删除

| 操作 | 对未来资源 | 对已有任务与文件 |
| --- | --- | --- |
| 暂停订阅 | 停止自动抓取、任务领取及新网盘写阶段 | 已提交 115 任务继续只读追踪；新建目录、提交、改名或移动均不得重新开始 |
| 立即检查 | 主动读取来源并更新候选 | 暂停状态下仅预览，不因此提交下载 |
| 恢复订阅 | 按各来源保存的规则恢复，先核对同资源既有意图 | 不自动重新提交未确认或已完成 Hash；不阻止同集其他 Hash |
| 归档订阅 | 停止采集，默认从活动列表移出 | 历史保留；已接受任务仍可核对，禁止新增写阶段 |
| 移除订阅 | 取消尚未领取的新任务，隐藏或软删除规则 | 不删除网盘文件，不清空 115 任务；未结束任务保留可访问的记录 |

暂停不声称能停止 115 已接受的离线任务。已经开始的文件改名或移动执行至可核实边界，不能中途切换设置或丢弃结果；操作前后均记录实际阶段。

首版将边界限定为已发出或已获准的单个外部写操作：确认其结果并持久化，不进入下一个写操作。P2-09 保留已确认的父/来源执行代次与基线，清除 RSS 和未获准写任务的租约、递增未认领选择的核验 generation，阻止旧领取继续；已获准单次写入保留结果确认。写操作在共享协调内复核状态和版本；改名完成但移动尚未开始时保留部分阶段，只有未知结果才最小补查后接续。新建暂停配置首次启用需有效预览；曾启用订阅的已确认意图不因预览过期丢失，来源/规则变化则需重新确认旧的未提交选择。

暂停/恢复/归档/移除本身及任务列表/详情都只读写本地 SQLite，不请求115；移除不清共享 Hash 认领或未结束任务入口。实现见[订阅控制](anime-subscription-control-implementation.md)。需要停止 115 任务或删除云端文件时，进入明确的独立操作，本功能不随暂停或移除自动执行。

## 8. 115 下载任务与恢复

### 8.1 状态分层

| 层 | 主要状态 | 依据 |
| --- | --- | --- |
| 订阅配置 | 待选资源草稿、启用、暂停、归档 | 草稿不参与调度；来源异常另存健康信息 |
| 发布决定 | 历史跳过、被过滤、待确认、已选中 | 本地规则及其版本 |
| 下载 | 排队、提交中、结果待核对、已接受、下载中、下载完成、失败、受阻 | 115 回执、后续状态与恢复结果 |
| 文件核对 | 未开始、核对中、已确认、待人工核对 | 本任务目录和实际文件身份 |
| 后处理 | 未启用、待执行、执行中、完成、部分完成、待核对 | 逐文件阶段记录 |

“下载完成”与“已确认实际文件”不是同一步；后处理只接受实际文件核对成功的输入。单任务与列表接口的状态码可能不同，分别规范化，未知值保留原始含义，不沿用“可重提”判断充当完成判断。

P0-03 实测同一完成任务在列表中为 `status=2`，精确查询为 `status=1/display_status=finished`；任务 `file_id` 指向目录而非视频。详见[115 验证报告](anime-p115-api.md)，未验证的状态和子文件能力不能据此当作已完成实现。

### 8.2 提交顺序

1. 校验订阅版本、启用状态、主账号及目录归属。
2. 事务领取任务，记录提交意图、固定来源 Hash、账号编号、核验 UID、目录及规则版本。
3. 获取本次执行的凭据内存快照；事务外访问 115。
4. 精确查询同资源任务。存在则核对归属与状态，不直接删除旧记录。
5. 明确不存在且本地没有未确认提交时，执行一次提交。
6. 保存已接受或结果待核对；若已接受但本地写回失败，凭提交意图在恢复时核对，不盲目重放。

自动订阅新增“确保提交并追踪”的业务入口，共享底层客户端、主账号验证和资源互斥；当前手动 `Submit` 的安全重提行为单独保留。不能把自动轮询直接接到会移除已结束任务记录的入口。

手动与自动入口必须使用同一份协调实例，并在写操作前核对实际 UID、协议和 Hash；只改自动入口的锁不能阻止手动入口并发删除或重提。协调范围的升级须保留原手动入口行为测试。若管理员显式重提本工具正在追踪的资源，界面提示关联任务，追踪侧转入重新核对，不沿用旧任务完成事实。

### 8.3 结果不确定与既有任务

- 超时、连接中断和进程重启发生在提交阶段时，先进入“结果待核对”。
- 任务未在某一页出现不等于不存在；完整读取失败不能作为不存在的证据。
- 同 Hash 在 115 中已存在但目标目录或本工具归属不明，显示“存在既有任务，需核对”，不接管其他工具的文件、不自动移走文件。
- 115 任务消失后，只核对本任务目录和已记录文件；无法确定时保留待核对状态，不自动重新下载。
- 只读查询可退避重试；写入结果不确定时先对账。人工重试产生新尝试记录，保留前一次结果。
- 115 已明确失败时可提供重试，执行前再精确核对；如需移除失败任务，仅移除确认属于本次资源的任务记录并保留文件。
- 首版建议失败下载由管理员重试；自动换资源、自动移除其他任务和自动清理不纳入默认策略。

### 8.4 重启恢复

任务用持久化阶段、版本与领取租约恢复。排队任务可以重新领取；提交中恢复为对账；已接受任务恢复只读追踪；已明确成功的步骤直接跳过，只有已发出但结果不明的步骤按记录最小补查，不能直接从头执行。

订阅已暂停或删除时，不恢复新的写阶段。后台退出由进程 Context 控制，所有工作协程可取消、可等待，不以浏览器请求生命周期承载长期任务。

### 8.5 完成后的终止边界

确认离线完成并核对到实际文件后，停止该条任务的离线状态轮询。未启用整理时到此结束；启用整理时仅推进本地记录中的文件改名、移动，不再通过离线列表判断整理结果。

选定视频和匹配字幕的改名、移动收到明确成功回执后，持久化完成并退出调度，不追加正常成功读回，不定期复查或重新下载。用户后续二次整理、移动、改名或删除不改变该处理结果，历史路径仅表示执行时位置。只有未完成、部分完成或写入结果不明的阶段需要恢复核对；本地 Hash、来源发布处理与文件记录仍保留，避免 115 记录被外部清理后重复提交。结束本地任务不要求自动删除 115 离线列表记录。

## 9. 主账号与凭据边界

- 统一使用明确创建的主账号，功能设置保存实际主账号编号与目录；不提供小号、个人网盘或播放池选择。
- 任务绑定账号编号、实际 UID、配置/规则版本和目录。文件记录绑定实际 UID 与文件 ID，不随账号配置换号转移。
- 下载长任务启动时固定账号凭据与设置的内存快照，后续轮询和文件核对沿用原快照；单次操作和同一长任务都不得随配置变化中途替换 Cookie、UID 或目标。后处理作为独立阶段启动时另行校验原任务身份和适用设置，再固定自己的执行快照。
- Cookie、签名和直链不进入任务、事件、列表响应或普通日志；凭据仍由既有账号服务管理。
- 主账号更换、删除或凭据清空后，阻止受影响的新写操作，要求重新确认本功能目录；不回退其他账号。
- 已交给 115 的任务不会因为本地换号而消失；旧任务保留原身份，无法访问时显示受阻。
- 服务重启不持久保存运行中的 Cookie。恢复时通过原配置重新验证身份；凭据版本变化的写阶段需重新核对后显式恢复，不能声称继承了原内存快照。
- 同 UID 重新认证可恢复对该身份的只读核对；跨 UID 不迁移任务、目录和文件归属。

## 10. 目录与文件核对

功能单独保存一个经过验证的“动漫下载目录”，归属于当前主账号；不隐式继承手动云下载或整理的目录。首版可与用户选择的现有目录一致，但归属需明确保存。

目录布局已由用户确定：先为每个番剧篇章建立可读名称的目录，再为每个实际下载资源建立独立子目录，例如：

```text
动漫下载目录/
  动画篇章名称 [本地条目短编号]/
    第07话 - 字幕组 [任务短编号]/
      原发布文件名.mkv
      原发布字幕.ass
```

实际归属以目录 ID 为准，路径只用于展示。任务子目录用于隔离文件核对；创建目录也是外部写入，需先记录意图，结果不确定时查找唯一匹配，不能连续创建多个同名目录。

未启用后续整理时，隔离目录是实际长期保存位置，不称为会自动清理的“临时目录”。启用第 11.1.1 节的自动整理后，它承接离线下载和文件核对，已明确选中的视频及其匹配字幕再归档到标准媒体目录；附件和空目录不随之自动删除。主界面与详情准确显示当前阶段及真实路径。没有可靠集号时使用经过处理的源发布名与任务短编号，不猜测命名。

这是一条下载资源一个目录，一条资源包含多个文件时共同保存在该目录。目录命名保留集号/来源信息与任务短编号，区分同名资源及后续人工选择的版本。标准媒体目录归档属于显式启用的后处理阶段，移动、冲突与中断恢复按第 11 节逐文件记录，不能为了隐藏目录层级默默移动文件。

下载完成后只列本任务目录，取得实际文件 ID、父级、名称、类型及列表附带大小，必要时展开结果子目录；直接复用列表行，不逐文件读元数据，不取或比对文件 SHA1。缺少清单时不按 RSS 标题猜文件 ID。

BT info-hash 继续用于资源幂等，不引入具体文件 SHA1 校验。P0-03 已观察到原始列表的 `wp_path_id` 和 `file_id`；同 Hash 精确查询缺少 `wp_path_id`，实测 `file_id` 对应目录，其 `pid` 与列表目标目录一致。现有规范化模型尚未提供这些关联字段。具体子文件的实站读取因后续接口异常未完成；P2 需补验证并实现严格文件核对，不能把目录关系视为全部文件已确认。

从任务目录列表行辨认结果标识类型，不另查对象元数据；仅在提交归属、目标目录与结果对象关系可靠时处理本任务目录。关联不足时采用已核对的专属目录边界，仍不能唯一确认文件则保留待核对，不自动整理。宽松解析得到的空列表、空/非法状态不能作为不存在或已完成的证据。

不做全盘扫描，不自动删除未选附件、原目录或旧版本。遇到多个视频、样片或无法判断对应集数时，列出实际文件供处理；自动后处理只运行在唯一且已核对的映射上。

## 11. 可选自动命名与归档

### 11.1 默认先形成独立的 115 下载能力

未关联 TMDB 时仍可保存、启用订阅和下载，文件保留原名。首个可交付版本以“可靠下载并确认文件”为完成边界。

后续提供可选自动整理：管理员选择目标作品、目标编号方案、字幕组对应规则与整理目录，预览后启用；后续符合已确认规则的任务在文件核对成功后自动改名和移动。未启用整理时，核对后的原文件保存在资源独立目录中。

#### 11.1.1 离线完成后的自动命名与归档

用户希望离线完成后，按 TMDB 作品名称、年份、ID 和映射后的季集号整理，并在文件名保留字幕组。这属于已规划的 P3 自动后处理能力，尚未实现；P2 只交付可靠下载与文件核对，不把完整自动命名写成已有功能。

建议采用以下默认模板，示例名称与 ID 按用户给出的文字展示，未在本轮校验该 TMDB 条目：

```text
整理目标目录/
  黑暗召唤师在地下恋爱中 (2026) {tmdb-335790}/
    Season 01/
      黑暗召唤师在地下恋爱中.S01E01.字幕组.mkv
      黑暗召唤师在地下恋爱中.S01E02.字幕组.mkv
      黑暗召唤师在地下恋爱中.S01E02.字幕组.zh-CN.ass
```

模板职责如下：

| 部分 | 来源与规则 |
| --- | --- |
| 作品目录 | `{TMDB作品名称} ({作品首播年份}) {tmdb-作品ID}`；按目标剧集资料取值，不能把某个 Bangumi 后续篇章的年份直接当作作品首播年 |
| 季目录 | `Season {两位季号}`；读取本订阅目标方案与已确认映射，特别篇明确指定时为 `Season 00` |
| 视频主名称 | `{TMDB作品名称}.S{季号}E{集号}.{字幕组}`；字幕组取该资源实际来源所确认的组名，不能统一写主源组名，保留原视频扩展名 |
| 外挂字幕 | 与唯一匹配的视频使用同一主名称，再保留已知语言、forced 等后缀及原扩展名；不猜测未知语言 |
| 名称处理 | 统一处理路径分隔符、非法名称与长度，预览显示处理后的准确结果；字幕组缺失或导致冲突时需确认，不用任意猜出的标签代替 |

字幕组是本工具的命名标签，TMDB 不提供字幕组资料；这里的“按 TMDB 命名”指使用已确认的作品资料和季集编排。已有手动整理支持标准作品/季目录，但其文件名模板和字幕组保留方式需提取后扩展，不能把它直接视为已经支持该自动流程。

自动执行顺序：115 返回下载完成 -> 核对实际文件身份与归属 -> 应用已确认季集对应 -> 固定命名和目标目录快照 -> 检查冲突 -> 云端批量改名/移动 -> 明确成功回执 -> 记录整理完成。

首次配置确认作品、对应规则、命名预览与目标目录后，后续符合范围且文件对应唯一的新任务自动执行，不要求每集重复确认。下载目录与整理目标目录分别绑定主账号配置及实际 UID；归档在同一主网盘内完成，不新增账号选择。使用 115 云端改名和移动，保留视频内容及扩展名，原名称、原路径和文件 ID 写入处理记录。

这里直接操作原文件，移动成功后原路径不再保留同一视频，不先复制再删除。本次改名、移动取得明确成功回执即可；只有超时或回执丢失才最小补查；完成后按第 8.5 节结束任务，不持续检查离线状态。附件与空目录仍按第 10 节处理，视频归档不等于批量清理源目录。

多字幕组同集以实际组名区分文件。不同资源完整目标路径相同（同组多画质/v2、组名清洗后重名等）时，只阻止受影响整理并保留下载文件，不阻止同集其他 Hash 下载、不覆盖旧版；需要明确版本标签后重新预览，不以随机后缀掩盖冲突。

映射未确认、实际文件无法唯一对应、目标同名、主账号/目录失效或写入结果不确定时，受影响的整理进入待处理/待核对，已完成下载结果保留。不中途换号、不自动覆盖或添加随机后缀掩盖冲突；每次改名/移动分别持久化步骤和结果，重启跳过已确认步骤，仅未知步骤最小补查。旧任务与历史文件仍需第 11.2.4 节的独立预览，保存新命名规则不触发批量改名。

### 11.2 整理命名映射

用户希望明确设计“字幕组发布集数对应 TMDB 哪一季哪一集”。建议采用**填写对应起点，系统计算偏移，先预览再保存**的方式；界面不要求用户心算正负偏移。此处的编号直接从字幕组原始集号出发，Bangumi 篇章内序号是辅助核对信息，不要求两层偏移相加后再猜目标。

#### 11.2.1 规则属于哪个字幕组

每份映射绑定本地篇章、资源订阅及已确认的来源编号空间，适用范围精确到所选来源/字幕组；同一作品的其他字幕组不会自动继承。更换字幕组时可以复制现有规则作候选，但必须重新预览并确认。映射与目标资料快照由本订阅独立保存。

目标默认使用 TMDB 原始季集；确需剧集组时，读取所选组并在本订阅保存独立快照和本地版本。复用现有 TMDB 元数据客户端、缓存和数据校验能力，避免依赖其他业务的全站编号设置或变更事件。面板显示本订阅的方案名称与版本，修改只作用于该订阅。剧集组目标编号与 TMDB 原编号不同时，在详情保留二者与实际分集 ID，避免都统称“TMDB 原集号”。

#### 11.2.2 常规情况：设置一组起点对应

位于订阅详情的“整理命名（可选）”中；默认收起，选择目标 TMDB 作品后再显示映射。首版建议从以下输入开始：

| 输入 | 示例 | 说明 |
| --- | --- | --- |
| 目标作品 | 管理员选择的 TMDB 剧集 | 与 Bangumi 篇章独立确认，不按名字自动绑定 |
| 目标方案 | 本订阅选择的 TMDB 默认季集或剧集组及快照版本 | 本订阅内预览保存，其他功能的设置变化不自动切换本方案 |
| 作为对应基准的字幕组话数 | 25 | 原始发布编号，不是“从第几集开始补”的下载下限 |
| 对应目标季 | 第 2 季 | 从本订阅目标方案选择 |
| 对应目标集 | E01 - 分集名称 | 从本订阅方案该季的分集列表选择，保留真实选中编号，不自动重置为第 1 集 |
| 适用范围 | 已确认的当前篇章，或字幕组第 25～36 话 | 常规无需预知连载终点；来源跨篇章或添加分段时再明确数字边界，不能无限延伸至后续所有季 |

常规表单采用连贯句式：“当字幕组标题为第 [25] 话时，对应目标 [第 2 季] [E01 - 分集名称]”；避免将两个孤立的“起始集数”输入框并排。目标分集选项来自该季列表，有剧集组编号差异时展示可查看的原编号说明；不靠裸数字输入猜测分集。计算规则：

```text
目标集号 = 字幕组集号 - 字幕组起始话数 + 目标起始集号
目标季号 = 本段选择的目标季

示例：25 -> S02E01，26 -> S02E02，36 -> S02E12
等价偏移：目标集号 = 字幕组集号 - 24
```

偏移量仅作为展开后的解释，不作为主要输入。上例只是编号算法样例，不代表《Re:0》的真实 TMDB 编排。

**下载起点与编号对应起点分开保存。** 例如规则仍为“25 对应 S02E01”，但管理员从字幕组第 30 话才开始补，第 30 话应对应 S02E06；不能把“从 30 开始补”误用成“30 对应 S02E01”。修改补番下限也不能改变已有编号对应。

输入下方即时回显：“当前从第 30 话开始补，第 30 话对应 S02E06”；如果当前资源中不存在第 30 话，则实际首个下载仍以资源预览为准，不承诺它必然找到。当前补番下限不落在本段时提示“此起点不在本段范围”，引导核对分段。

连载篇章尚无可靠终点时，默认范围选项可为“仅适用已确认的当前篇章正片”，前提是来源关联已经能识别该篇章；新资源的篇章归属和目标集号仍要核对。来源混合多篇章又不能可靠区分时，必须先限定范围，不能用这个选项代替事实确认。不能用预计总集数臆造终点，也不因超出已确认目标范围就顺延到下一季。

#### 11.2.3 跨季与例外：分段规则和逐集指定

常规表单下提供“添加一段对应”和“单集例外”，按需展开，不初始铺满规则编辑器。例如同一来源在已确认范围内连续编号，但目标拆成两季：

| 字幕组发布范围 | 对应目标 | 规则 |
| --- | --- | --- |
| 第 1～12 话 | S01E01～S01E12 | 本段 1 对应第 1 季第 1 集 |
| 第 13～24 话 | S02E01～S02E12 | 本段 13 对应第 2 季第 1 集 |
| SP01 | S00E01（人工指定） | 特别篇不参与正片整数偏移 |

每条来源分别保存编号映射。规则匹配先查单集例外或明确忽略，再匹配唯一适用的连续段；没有匹配则进入“待设置对应”。同一来源的连续段不重叠，单集例外可覆盖段内结果，预览明确标识。一个来源的两个不同剧情分集不能误映射成同一目标集；不同字幕组或同集不同资源版本对应同一目标季集属于正常共存，完整目标路径冲突才阻止相关整理，不覆盖旧文件。

12.5、SP、OVA 等保留原始类型和字符串编号，只走明确的逐集指定，不用浮点数套整数偏移。新编集两话合一、一个文件拆成多个目标集、需合并/裁切的版本不使用偏移自动解决：保留原文件供人工确认。首版逐集规则只支持一条原始分集对应一条目标分集或明确忽略；跨多个 TMDB 作品时按本地篇章拆开配置。

“跳过自动整理”仅保留本次原名文件，不自动排除下载；若不想下载特别篇，使用订阅的资源筛选条件，界面说明两个动作的范围。

#### 11.2.4 预览、保存与生效边界

桌面预览列表并列展示“资源原标题、字幕组话数、对应目标季集/分集名、采用规则、核对结果”，篇章内集号作为可选辅助列。手机按资源显示紧凑行，先显示“第 25 话 -> S02E01”；正常行保持简洁，有例外或异常时在行内显示“单集指定”“目标暂缺”“对应冲突”等文字及项目 SVG 提示，点击查看详情。顶部显示需处理数量并可筛选，不强迫逐行展开找问题，也不将全部列压成横向大表格。

预览覆盖当前已加载发布和已确认文件，显示范围；显示正常、目标暂缺、规则未覆盖、重复目标等具体结果。未来尚未发现的发布只能按已保存规则核对，不能显示为“全部映射成功”。目标分集未在本订阅方案中存在、集号小于 1、目标季不存在、规则重叠或对应冲突时阻止受影响的自动整理；原文件订阅下载可独立继续。

目标方案快照尚未包含新集时，本订阅可“检查资料更新”，展示差异后确认更新本订阅快照，再重新预览。默认季集与剧集组统一按本订阅版本核对，不改动其他业务的资料。目标资料暂时不可用时，沿用可用的已保存快照进行可验证范围内的核对；没有有效快照则该整理阶段等待处理，不把未取得的目标资料当作不存在。

保存携带映射版本、来源绑定版本、本订阅目标方案版本及预览指纹；冲突返回可识别错误并要求重新预览，保留输入。保存映射只用于保存后新建下载任务的整理计划，旧下载/整理任务继续使用原快照，不套用新规则。按用户确认取消历史补整理，不提供“应用到已有任务/文件”入口，也不因保存偏移触发旧文件移动。

已开始的文件写阶段固定映射和文件名快照；未开始阶段保留原计划，若本订阅映射/目标方案已经变化则转为需重新预览，不能静默换用新版本。TMDB 删除或不可用不影响继续订阅和保存原文件，但缺少有效资料快照的新整理进入待处理。保存规则不直接把文件标为整理完成，实际结果以 115 文件身份、名称和目录读回为准。

#### 11.2.5 后端表示与验收样例

`anime_naming_mappings` 保存目标 TMDB ID、本订阅方案 ID/快照及本地 revision、映射 revision、来源编号空间和确认依据；其连续段、逐集例外分别用结构化子记录保存，不执行用户表达式，不使用只有一个裸偏移数字的全局设置。每段保存源类型、起止范围/已确认篇章范围、源起点、目标季和目标起点；逐集例外保存原始分集身份及目标或忽略动作。

映射器为纯函数，输出目标编号或明确未匹配/冲突原因；目标方案核验使用固定快照，网络调用不放进事务。保存只更新对应来源的规则与版本，下载 Hash、资源幂等记录和旧任务快照保持稳定。

关键验收包括：25 对应 S02E01 时 30 对应 S02E06；从 30 开始补不改变对应；字幕组从 1 重置可独立对应另一季；两段边界不重叠；SP 走单集指定；源条目跨篇章、两个源集指向同一目标、目标暂缺、方案切换及规则保存后处理旧文件的行为均可解释。

### 11.3 复用范围

现有 `ManualOrganize` 依赖 TMDB，任务历史位于独立配置文件，重启后中断且不自动续写。应提取命名、文件身份检查、冲突检查及改名/移动的底层能力，为自动流程增加独立的持久化执行阶段；不把手动接口直接当成后台可恢复队列。

现有目录监控包含移动、创建分享与清理等行为，不能整体挂到动漫下载完成事件。动漫整理只接收本任务已核对的精确文件集合，复用基础文件能力，不触发其他业务流程。

整理与手动整理共用目录工作协调，改名/移动前后读回核对。不覆盖同名文件，失败保留阶段；其他工具并发改文件时不能承诺跨工具事务原子性。

### 11.4 整理完成判定

未启用整理时，以已确认的下载文件保存在任务目录中作为该资源的完成结果。启用整理后，选定视频及匹配字幕均须按计划改名/移动，并读回核实实际 UID、文件 ID、目标目录、名称和大小；全部所选文件核实后才记录“整理完成”。

整理完成是本条执行的终态：停止后台调度和离线轮询，保留去重与处理记录。之后外部工具移动或删除文件不使本模块自动重开旧任务；管理员另行发起的已有文件处理按第 11.2.4 节执行。

部分完成、写入不确定、规则未覆盖或冲突分别保留对应状态；附件原位保留不算整理失败。统计只使用本模块确认的分集和文件，不把源站最大集号或预计总集数当作整部已完成。订阅是否归档仍按第 4.3 节的独立规则处理。

## 12. 持久化设计建议

沿用 SQLite，不新增 Redis、MySQL 或独立 Java 服务。P0-05 的[数据与接口契约](anime-subscription-contract.md)及[可执行 DDL](anime-subscription-schema.sql)为后续实现依据；以下是职责概览，不再作为最终字段定义。生产迁移按 P1/P2/P3 接入，不在文档阶段修改应用数据库版本：

| 表/实体建议 | 主要内容 |
| --- | --- |
| `anime_entries` | 稳定本地 ID、Bangumi 篇章名称及来源原名、版本/篇章、可选系列关系、外部 ID、资料快照 |
| 来源绑定（嵌入 `anime_subscription_sources`） | 本地篇章、Bangumi/蜜柑关联、字幕组适用范围、原始编号空间、篇章内编号对应、确认依据与版本；最终契约不另建 `anime_source_bindings` |
| `anime_subscriptions` | 本地篇章、草稿/启用/暂停状态、整体配置版本、主来源标识、下载/整理目录绑定及公共设置；启用时校验已选来源完整性 |
| `anime_subscription_sources` | 所属订阅、主/备用角色、来源关联、实际字幕组、独立筛选/下限/编号、启用计划、基线/预览边界、健康状态与版本 |
| `anime_releases` / `anime_release_decisions` | 原帖身份、可碰撞 GUID、原始标题/日期/解析观测，以及各来源独立发布决定、取消选择与待核验调度 |
| `anime_resources` | 仅保存已验证的协议/Hash 与证据；不同发布可以关联同一资源 |
| `anime_preview_batches` / `anime_source_previews` / `anime_preview_items` | 总配置指纹、逐来源有效期/加载版本与不可混淆的发布快照；不等于下载基线 |
| `anime_source_baselines` / `anime_baseline_releases` | 首次启用确认的独立 T0、版本及已见集合；不因临时预览清理而丢失 |
| `anime_settings` / `anime_request_keys` | 功能主账号目录绑定和配置版本，以及与本地管理变更同事务提交的幂等回执 |
| `anime_resource_claims` | 选中发布、已核验资源、当前任务与幂等认领；唯一约束限同资源/操作，不对分集号设独占 |
| `anime_download_jobs` / `anime_job_selections` | 账号/UID、目录、尝试历史、下载/文件/工作阶段、租约、关联来源授权及固定设置快照 |
| `anime_files` / `anime_job_files` | 实际 UID/文件 ID 与任务精确集合、原目录/名称/大小/SHA1、视频/字幕/附件选择及核对事实 |
| `anime_naming_plans` / `anime_naming_mappings` | 本订阅独立目标快照与方案版本、各来源编号空间及结构化分段/逐集例外 JSON；最终契约不单建 segment/override 表 |
| `anime_action_previews` | 命名/资料差异/已有文件整理预览，独立于 RSS 的追新 T0 |
| `anime_postprocess_jobs` / `anime_postprocess_items` / `anime_drive_operations` | 精确文件与命名快照、逐文件阶段，以及每一次外部写操作的意图/授权/核对结果 |

首版一个订阅含一个主来源及可选备用列表，各自独立运行、共同遵守站点预算，不做主源覆盖备用的优先替换。相同源的网络读取按规范化来源键合并；同 Hash 在不同发布记录中保留关联，不反复执行，不扩大成同集资源互斥。

Bangumi 日历、搜索与详情缓存保存响应时间、成功版本及过期信息，可复用现有缓存基础设施；不为缓存额外引入数据库或服务。草稿允许缺来源和目录，启用订阅不允许，后端用明确状态约束区分。篇章资源关联与 TMDB 命名映射分别存储和版本化，修改后不覆盖已有任务的来源快照。

来源分页记录可归档，完整原始 RSS 无需无限保存。规则决定与资源归属需保留足够摘要，完成 Hash 与来源发布处理记录不能随界面历史清理而删除，否则会反复提交同资源。历史清理采用显式保留策略，不在首版默认清除幂等依据。

数据库事务只保存意图、领取和结果，不包住网络请求；内存索引仅在提交成功后更新。沿用单进程实例锁和现有 SQLite 写入约束，不对外宣称支持多实例抢占执行。

## 13. 后端模块与接口建议

按 Go 后端工程规约分层，先采用窄接口，具体文件可随实现调整：

| 层 | 职责 |
| --- | --- |
| `backend/internal/client/mikan` | 扩展受控 RSS 读取，复用来源校验与限流 |
| `backend/internal/client/bangumi`（新增） | 首版实现周历、历史搜索、按需详情与缓存；受控上游地址和请求预算，不参与下载授权 |
| `backend/internal/client/p115` | 复用云下载 API，补充状态规范化与完成文件字段 |
| `backend/internal/model` | 条目、规则、发布、任务、文件和映射数据类型 |
| `backend/internal/storage` | 新增表、事务去重、任务领取、租约、查询与恢复 |
| `backend/internal/service` | 独立的动漫订阅、纯解析/筛选、调度、115 对账、纯编号映射与可选整理；外部依赖限于小接口的元数据和网盘能力 |
| `backend/internal/httpapi` | 管理员鉴权、参数校验、幂等操作、分页和结构化错误 |
| `backend/cmd/server` | 仅装配依赖、启动与等待退出 |

解析与筛选尽量为不访问网络的纯函数；资源来源、下载网关、文件检查和存储通过小接口组合。网络、数据库、耗时操作均接收 Context，错误逐层包装，由边界统一记录；所有后台协程均可取消且纳入退出等待。

API 统一放在 `/api/admin/anime`，下列为能力概览；最终请求字段、阶段闸门、逐源错误及响应投影见[接口契约第 7、8 节](anime-subscription-contract.md)：

- `GET /discovery/calendar`：服务端缓存的 Bangumi 周历，返回源资料时间与缓存状态，不接受未经验证的季度参数。
- `POST /discovery/search`：Bangumi 历史作品搜索，上游参数按 P0 核实结果设计。
- `GET /discovery/subjects/:id`：按需读取 Bangumi 篇章详情和关系。
- `POST /sources/mikan/search`：为所选篇章查询蜜柑候选，也支持管理员手动关键词。
- `GET /sources/mikan/:id`：番剧条目及字幕组信息。
- `POST /source-bindings/preview`：预览来源篇章覆盖范围与编号对应，确认后由订阅保存过程持久化。
- `POST /subscriptions/preview`：来源、规则、起始集、历史加载边界与候选结果，返回可延续加载的预览标识。
- `POST /subscriptions`：保存草稿，或根据有效预览创建暂停/启用订阅，携带幂等键；启用必须通过完整校验。
- `GET /subscriptions`、`GET /subscriptions/:id`：分页列表与详情。
- `PATCH /subscriptions/:id`：按 revision 更新配置，不隐式重提旧任务。
- `POST /subscriptions/:id/pause|resume|check|archive`：明确行为的管理动作。
- `GET /subscriptions/:id/releases`：分页资源记录、决定和执行摘要。
- `GET /jobs/:id`、`POST /jobs/:id/reconcile|retry`：查看、核对与显式重试。
- `GET/PATCH /settings`：当前主账号对应的功能目录与调度设置。
- P3 新增 `POST /subscriptions/:id/naming-mapping/preview`、`PUT /subscriptions/:id/naming-mapping`，以及本订阅目标资料检查/确认更新、已有文件整理预览/执行接口；下载创建不依赖它们。

所有执行资格在后端检查；前端禁用控件不能替代版本、角色、目录、主账号和任务状态校验。GET 不触发云端写入，关闭详情只取消查看请求，不取消长期后台任务。

## 14. 请求量与性能建议

下表部分数值仍为性能初始建议；RSS、历史预览和暂停/终态行为已按[首版规则](anime-first-release-rules.md)固定为实现默认，均不是上游保证的限额。性能结论仍待相应阶段验证：

| 项目 | 初始建议 |
| --- | --- |
| Bangumi 日历 | 服务端共享缓存，初始有效期建议 1 小时；过期可先返回带时间的旧数据并合并刷新，首次无缓存失败显示真实错误 |
| Bangumi 搜索/详情 | 搜索防抖、规范化关键词缓存和请求取消；只对当前选中的作品补详情，不逐卡请求蜜柑 |
| RSS 周期 | 每个启用源/组 15 分钟、最多 60 秒错峰；手动检查 60 秒内复用有效结果，共享访问与冷却限制 |
| 来源请求 | 沿用蜜柑至少 1 秒间隔与进行中请求合并，自动抓取避免挤占交互请求 |
| 条件读取 | 上游支持时使用 ETag/Last-Modified；不支持则正常读取，不能把失败当 304 |
| RSS 保护 | 新动漫读取单次正文 4 MiB、最多 2000 条原始发布，超限报未读完整，不悄悄截断后判断无更新 |
| 初次补历史 | 每次最多 3 请求/45 秒/8 MiB，各来源已加载快照合计最多 2000 条；每来源预览各自 15 分钟有效，继续加载不续期，不预抓全部番剧 |
| 115 追踪 | 只检查本工具未完成任务，间隔2～5分钟、异常退避；P2-08已统一调整调度，完成并取得一次清单后停止 |
| 追踪查询 | 不全量翻页；提交确认与首轮追踪合并，同任务合并重复触发，页面仅读本地状态 |
| 创建资源目录 | 正常仅1次POST，成功CID直接保存；回执不明才列固定父目录恢复 |
| 下载文件清单 | 文件直接在任务目录时通常1次列表；结果是内层目录时通常2次列表，必要分页/子目录除外；无逐文件GET或SHA1查询 |
| 整理目录/冲突 | 按固定UID和目标路径缓存，批次共用目录及冲突列表，不逐文件重复读取 |
| 改名/移动 | 使用批量接口，明确成功不补查；只有未知回执才按记录对象最小补查 |
| 完成之后 | 0次定时115请求，不验证原位置，不追踪二次整理，不自动恢复或重下 |
| UI 更新 | 仅可见列表/详情约 30 秒读取本地状态，先恢复成功缓存；后台页面停止刷新，上游调度独立 |
| 网盘写入 | 单 UID 保守串行，复用已有账号限流和目录工作协调 |
| 封面 | 本地缓存、懒加载、请求合并，资料补充不逐卡片重复请求 |

抓取、下载、页面详情与文件整理分别调度，不让一次慢 115 请求阻塞全部订阅。401/403、风控或 429 进入相应暂停/退避并遵守 Retry-After，不提高并发重试。

新增可观察数据：每轮请求数、条件缓存命中、排队长度、任务阶段耗时、失败类别与恢复次数。实际性能结论通过模拟负载与受控只读观察给出，不预先声称“零开销”。

### 16.1 有意义的后端测试

- 资源解析：年份/画质干扰、连续编号、12.5、SP、无日期、修正版、未知协议、种子 Hash。

Gemini CLI 对修订版的交互审阅已完成，采纳：

- 创建面板按来源、规则、预览的依赖逐段展开，手机操作区只显示当前动作。
- 部分历史未加载时提供继续加载，并明确本次仅下载已预览的选择。
- 对未完成草稿、读取失败、零匹配、存在历史候选分别定义按钮与保存结果。
- 详情先复用已有资料，再分块补数据；预览后新增资源另行检查，规则变化/预览过期保留输入并重新预览。
